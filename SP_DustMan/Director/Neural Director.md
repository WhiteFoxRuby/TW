# Neural Director — roadmap GRU/Transformer

> [!summary]
> План перехода от rule-based режиссёра к нейросетевому, который читает **историю событий игрока** и выбирает следующий блок контента. Нейросеть не генерирует правила, цены, поломки или текст — она **выбирает из безопасной библиотеки блоков**, и любое её действие проходит валидатор. Текущий `GameDirector` остаётся baseline; GRU/Transformer сначала работает в **shadow mode**. Создано 2026-07-10; рабочий план, не скоуп среза.

```text
история событий игрока → оценка скрытого состояния → допустимые блоки → выбор блока → валидация → применение
```

## Принципы

- Нейросеть не решает вне грамматики: выбирает из разрешённых действий.
- Правила, которые игрок выучил, не меняются: слоты, инструменты, поведение ремонта.
- Любое действие модели проходит валидацию.
- Нейросеть сначала советует, потом управляет.
- Награда и тесты детерминированы, **без LLM-судьи** в контуре оценки.
- **Данные важнее модели:** без событийного лога GRU/Transformer будет декоративным слоем.

## Три слоя

1. **Среда** — игра и её факты: деньги, слоты, предметы, ремонт, продажи, события.
2. **Политика** — правило, GRU, Transformer, LLM или replay.
3. **Валидатор** — обязательный слой: кулдауны, бюджет, доступность блока, запреты.

Финальная архитектура и контракты уже реализованы базово — [[Director/Director#Пайплайн решения]].

## Токены событий

Каждое событие лога превращается в токен для последовательной модели:

```text
event_type_embedding · item_id_embedding · defect_id_embeddings · director_action_embedding · numeric_features · time_delta
```

Окно для старта — **64 события**; после недельного цикла — 128–256. `DirectorEventToken` уже собирается в `DirectorObservation.RecentEvents`.

## GRU-политика (первая)

Дешевле и проще Transformer.

| Вход | Выход |
|---|---|
| последовательность N событий | `pressure_hat`, `boredom_hat`, `frustration_hat` — оценка скрытого состояния |
| агрегированная observation | `player_style_logits` — экономный / рискованный / коллекционерский / быстрый / осторожный |
| маска допустимых действий | `action_logits` — вероятности блоков |
| | `risk_hat` — риск плохого исхода в ближайшем окне (застревание, отказ, просадка) |

В рантайме `action = argmax(masked_action_logits)`; мягкий sampling с температурой — только после тестов (воспроизводимость).

## Transformer-политика (позже)

Оправдан, когда появятся длинные нарративные цепочки, категории предметов, вылазки, чернота, покупатели с историей, недельные события и достаточно телеметрии. Лучше видит дальние зависимости: игрок давно избегает продажи, оставляет необычные предметы, забывает зацепку.

```text
Transformer = долгосрочный планировщик
Rule-based validator = безопасность и правила
```

Не рекомендуется: Transformer напрямую меняет экономику, правила ремонта или цены.

## Обучение — шесть этапов

| Этап | Что | Зачем |
|---|---|---|
| **1. Imitation learning** | учитель — `GameDirector`; данные: observation, event_history, allowed_actions, rule_based_action | модель учится формату задачи и копирует безопасную политику |
| **2. Prediction heads** | предсказывать: успешна ли продажа, провал проверки, число ошибок, изменение денег, бездействие | представление о последствиях — полезнее раннего RL |
| **3. Симуляторные прогоны** | профили: экономный, коллекционер, быстрый, осторожный, рискованный продавец, уставший | дешёвые регрессионные прогоны; симулятор — не «истина» |
| **4. Offline evaluation** | решения на записанных историях без влияния на игру; сравнение rule-based / neural / validator / predicted / actual | безопасная оценка |
| **5. Shadow mode** | в игре работает rule-based; нейросеть предлагает рядом, логируем расхождения | только после этого — управление частью ручек |
| **6. Controlled rollout** | см. ниже | постепенная передача контроля |

### Controlled rollout

Сначала нейросеть управляет только **безопасными ручками**: знакомый/разнообразный лут, момент мягкой зацепки, тип покупателя, фоновое событие без экономического удара.

**Запрещено на первом rollout:** менять аренду; резко ухудшать рынок; ускорять черноту; менять правила ремонта; выдавать тяжёлые события без инструментов ответа. Обязательны rule-based fallback и аварийный выключатель.

## Тестирование

- **Unit:** observation builder собирает признаки; маска запрещает недоступные блоки; валидатор режет cooldown / бюджет / предусловия; лог сохраняет причинную цепочку. *(Тестовой сборки в проекте пока нет — [[Reference/Roadmap#Критично]].)*
- **Golden scenarios:**

| Сценарий | Ожидаемая реакция |
|---|---|
| Мало денег, много отказов | щедрее рынок, мягче покупатель |
| Много ошибок жестов | знакомые предметы, меньше новых механик |
| Много пустых слотов | лёгкая зацепка или полезный заказ |
| Долго нет сюжета | зацепка в доступном канале |
| Игрок стабилен и богат | больше разнообразия, без наказания |

- **Monte Carlo:** тысячи прогонов на профилях — не спамит ли один блок, не уводит ли экономику в минус, не превращает ли игру в постоянную помощь, не нарушает ли кулдауны, не теряет ли зацепки.
- **Метрики:** `fit_to_target_curve, pressure/boredom/frustration_recovery_days, action_diversity, budget_violations, cooldown_violations, lead_delivery_rate, lead_resolution_rate, economy_survival_rate, rubber_banding_visibility` (последняя — плейтест-вопрос «казалось ли, что игра подыгрывает?»).

## Ближайший практический шаг

Не обучать модель сейчас. Сначала:

1. Починить списание слота ремонта: при начале ремонта или первом значимом действии, а не только при завершении.
2. Починить доставку зацепки: `LastLeadDay` обновлять по факту `LeadSeen`/`LeadAcquired`, а не при генерации рынка.
3. Расширить профили игрока, поднять объём до 1000+ дней, добавить pass/fail-пороги качества policy и экспорт train/validation split для GRU.
4. Закрыть расхождения rule-based ↔ маска и валюту бюджета ([[Director/Director#Пайплайн решения]]).

После этого rule-based режиссёр станет нормальным baseline для обучения.

## Связь с DirectorBench

[[Director/DirectorBench]] полезен как методология: дискретная грамматика блоков, детерминированная награда, симулированные и hold-out профили, сравнение rule-based / random / neural / LLM, проверка Goodhart-разрыва. Но продукт и исследование не должны смешиваться слишком рано: в игре сначала нужен устойчивый и понятный режиссёр; в исследовании можно проверять более рискованные модели.
