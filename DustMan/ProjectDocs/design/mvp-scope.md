# MVP-скоуп: вертикальный срез

Рабочий документ для агента-разработчика: что строим, в каком порядке, как проверяем. Создан 2026-07-08.

Статус: утверждённый скоуп среза. Отступления от полного дизайна помечены как «упрощение среза» - их можно оспаривать в чате, но не расширять молча.

## 1. Цель среза

Проверить главную гипотезу игры: **жестовый ремонт за столом приятен сам по себе**. Всё остальное - обвязка, чтобы ремонт имел контекст (купил сломанное → починил → продал).

Срез = один играбельный день: рынок → ремонт карманного фонаря по трём фазам → продажа покупателю. Если после сборки среза чинить фонарь скучно - меняем дизайн жестов, а не добавляем контент.

## 2. Границы скоупа

**Входит:**

- Один предмет: карманный фонарь (упрощённый Пример 1 из [механик починки](../features/repair-mechanics.md)).
- 6 жестов: вращение, перетаскивание, протирка, качание, клик, зум.
- 5 инструментов: отвёртка, плоскогубцы, тряпка, лупа, наждачка.
- Три фазы ремонта: Осмотр → Работа → Проверка.
- Рынок (покупка фонаря за деньги) и продажа (один покупатель, цена жестом по шкале).
- Дневной цикл из 4 тайм-слотов (упрощение среза: рынок = 1 слот вместо вылазки за 2).
- Деньги. Плейсхолдер-арт (цветные спрайты, как в текущем прототипе).

**Не входит (сознательно):** чернота, вылазки и раскопки, блокнот, апгрейды мастерской, типы покупателей (один универсальный), обвал рынка, аренда (флаг в конфиге, по умолчанию выключена), AI-режиссёр, сохранения, пайка и точное перетаскивание (жесты hold / drag-по-траектории), звук (этап опционален), геймпад и тач, локализация, Spine-анимации.

## 3. Игровой цикл среза (walkthrough)

1. Игрок в хабе (существующая side-scroll сцена), 4 слота дня, 100 монет.
2. Подходит к точке «Рынок» → UI рынка: 2-3 фонаря с разными видимыми состояниями и ценами (15-25). Покупка списывает 1 слот и деньги.
3. Подходит к точке «Верстак» → сцена/экран верстака. Ремонт списывает 1 слот.
4. **Осмотр:** фонарь на столе, вращается перетаскиванием, зум колесом. Видимые дефекты заметны, скрытые - через лупу или после разборки. Маркеров «что сломано» нет.
5. **Работа:** разборка (отвёртка - вращение), устранение дефектов инструментами, сборка обратно.
6. **Проверка:** клик по кнопке фонаря. Все дефекты устранены → луч света, успех. Нет → симптом (не включается / мигает), возврат к работе без штрафа.
7. Подходит к точке «Прилавок» → продажа: покупатель, шкала цены жестом, реакция лицом (доволен / думает / уходит), сделка. 1 слот.
8. Конец дня: сводка (потрачено/заработано), новый день.

## 4. Контент среза

### Фонарь: модули и дефекты

Модули: корпус, линза, лампа+контакты, батарейный отсек, кнопка. У экземпляра 2-3 случайных дефекта из пула:

| Дефект | Модуль | Виден | Инструмент и жест | Симптом на проверке |
| --- | --- | --- | --- | --- |
| Грязный корпус | корпус | сразу | тряпка, протирка | нет (влияет на цену) |
| Окисленные контакты | отсек | после разборки | наждачка, качание | не включается |
| Погнутая кнопка | кнопка | сразу | плоскогубцы, клик+drag | кнопка не нажимается |
| Треснутая линза | линза | только лупой | замена из запаса, drag | светит тускло |
| Севшие батарейки | отсек | после разборки | замена из запаса, drag | не включается |

Запасные линзы и батарейки лежат в ящике на столе, бесплатны и бесконечны (упрощение среза).

### Баланс (черновые числа, конфиг в одном месте)

| Параметр | Значение |
| --- | --- |
| Стартовые деньги | 100 |
| Цена фонаря на рынке | 15-25 (хуже состояние - дешевле) |
| Базовая цена починенного | 60 |
| Модификатор качества | ×0.7-1.3 (чистота, все дефекты устранены, без перекрутов) |
| Слоты дня | 4; рынок 1, ремонт 1, продажа 1 |
| Аренда | 150 в конце дня 7, по умолчанию выключена |

Качество 0-100 считается детерминированно: 40 за устранение всех дефектов + 30 за чистоту + 30 минус штрафы за ошибки жестов (перекрут, лишние царапины).

## 5. Технический каркас

Проект: Unity 6000.3.8f1, URP 17.3, Input System 1.18 (пакет уже подключён - использовать его, а не сырой `Keyboard.current`; см. ревью кода).

### Структура данных (ScriptableObject, папка `Assets/Data/`)

- `ItemDefinition` - предмет: список модулей, базовая цена, спрайты.
- `ModuleDefinition` - модуль: точки крепежа (винты), слоты деталей, допустимые дефекты.
- `DefectDefinition` - дефект: где виден (сразу / лупа / после разборки), инструмент, жест, параметры (число оборотов, площадь протирки), симптом.
- `ToolDefinition` - инструмент: жест, к каким дефектам применим, спрайт.
- Экземпляр предмета (runtime): `ItemInstance` - список модулей с состояниями и дефектами, прогресс каждого дефекта.

### Жестовый ввод (ядро, `Assets/Scripts/Gestures/`)

`GestureRecognizer` - MonoBehaviour, активируется при захвате точки взаимодействия, отдаёт события прогресса:

- **Вращение:** накапливать угловую дельту вектора курсор→центр точки за кадр; знак = направление. Порог срабатывания ~30°/кадр-окно, полный оборот = 360°. Винт: N оборотов против часовой = выкручен; больше N+2 по часовой = перекрут (штраф качества).
- **Протирка:** маска загрязнения (grid 8×8 на спрайте модуля); ячейка очищается при проходе курсора с зажатой кнопкой; дефект снят при 90%+.
- **Качание:** смена знака дельты по доминирующей оси; одно «качание» = ход туда-обратно ≥ мин. амплитуды; K качаний = готово.
- **Drag:** стандартный, со снапом к слотам (подсветка валидного слота).
- **Клик, зум** - тривиальны.

Все пороги - в конфиге, не в коде: их придётся крутить на плейтестах.

### Сцены и порядок экранов

Хаб - существующая `SampleScene` (ходьба уже работает). Рынок и прилавок - UI-оверлеи поверх хаба, открываются через существующий `InteractivePoint` (клавиша E). Верстак - отдельная сцена `Workbench` (переход тоже через InteractivePoint, возврат по Q - паттерн InteractionScene уже есть в проекте).

### Судьба текущего кода (см. ревью в чате от 2026-07-08)

- Починить утечку: кэшировать спрайт из `CreateWhiteSprite()` в static-поле; вынести дубли в `SpriteUtils`.
- Вынести генерацию уровня из `PlayerController` в `LevelBuilder`.
- Позицию между сценами передавать через static-класс `SceneCarry`, не PlayerPrefs.
- `CameraFollow`, `InteractivePoint` - переиспользовать; `AutoSprite` - заменить на `SpriteUtils`.
- Ввод перевести на Input Actions (asset уже в проекте: `InputSystem_Actions.inputactions`).

## 6. Этапы и критерии приёмки

Порядок жёсткий: каждый этап проверяется человеком до перехода к следующему. После этапа - запись в [WORKLOG](../WORKLOG.md).

**Этап 0 - санация прототипа.** Багфиксы из списка выше. Приёмка: поведение хаба не изменилось, дублей `CreateWhiteSprite` нет, ввод через Input Actions, стрелки работают наравне с WASD.

**Этап 1 - каркас данных.** SO-типы, `ItemInstance`, генератор экземпляра фонаря (2-3 случайных дефекта). Приёмка: в тестовой сцене кнопка «сгенерировать» печатает в консоль состав фонаря с дефектами; 20 генераций дают разные комбинации.

**Этап 2 - GestureRecognizer + дебаг-сцена.** Все 6 жестов на голых прямоугольниках, без предмета. Приёмка: сцена `GestureDebug` с индикаторами прогресса каждого жеста; человек руками подтверждает, что вращение/протирка/качание детектятся надёжно и не срабатывают друг вместо друга. **Это ключевой этап - если жесты не ощущаются, дальше не идём, а крутим пороги.**

**Этап 3 - верстак.** Сцена Workbench: фонарь на столе, инструменты лежат на столе (drag к точке работы), разборка/сборка по модулям, зум. Приёмка: полный цикл «разобрал - устранил окисление - собрал» мышью, без UI-кнопок.

**Этап 4 - фазы и дефекты.** Осмотр (без маркеров, лупа показывает скрытое), все 5 дефектов, Проверка с симптомами, расчёт качества. Приёмка: фонарь с «не включается» диагностируется и чинится без подсказок интерфейса; недочиненный показывает правильный симптом.

**Этап 5 - экономика.** Рынок, прилавок, шкала цены жестом, реакция покупателя, деньги, слоты дня, сводка дня. Приёмка: полный день-цикл из раздела 3 играется от начала до конца; купить дешевле - починить лучше - продать дороже даёт положительную маржу.

**Этап 6 (опционально) - фидбек.** Плейсхолдер-звуки (щелчок, скрежет, протирка), твины реакции предмета. Приёмка: субъективно «стало приятнее» на плейтесте.

## 7. Критерий готовности среза

Человек, не видевший доков, за 10 минут без объяснений проходит день-цикл и правильно отвечает на вопрос «что ты делал?». После этого - плейтест-вопрос гипотезы: «хочется починить второй фонарь?» Ответ «да» → расширяем контент (второй предмет - ожерелье). Ответ «нет» → дизайн-итерация жестов, контент не добавляем.

## 8. Правила для агента-разработчика

- Код - в `Assets/Scripts/` (подпапки Core / Gestures / Workbench / Economy / UI), данные - в `Assets/Data/`. `ProjectDocs` Unity не импортирует - туда только документация.
- Все числа баланса и пороги жестов - в конфигах/SO, не в константах кода.
- Не расширять скоуп: всё из списка «не входит» требует явного решения владельца проекта.
- После каждого этапа: запись в WORKLOG, при новых документах - обновить индексы (правила в [_service/CODEX.md](../_service/CODEX.md)).
- Термины - по [глоссарию](./glossary.md); дизайн-контекст - [БГДД](./gdd.md), [блюпринт верстака](./workbench-blueprint.md), [механики починки](../features/repair-mechanics.md).
